# 设计规范 · Yuki Design System

> **版本**：v1.2
> **基于**：Apple HIG · Anthropic Brand · Linear · Vercel Design
> **设计工具链**：Figma（高保真）· Axure（动态原型）· 墨刀（移动端 MVP）· Xmind（架构）

---

## 0 · 设计工具链

| 工具 | 用途 | 产出量 | 文件归档 |
|---|---|---|---|
| **Figma** | 对话界面 + 数据看板高保真原型 | **15+ 页** | 团队空间 / Yuki / Final |
| **Axure** | 核心交互动态原型（黄金路径可点击） | 3 个原型集 | Axure Cloud Share |

- Figma 强在**协作 + 组件库**，适合做最终高保真
- Axure 强在**动态交互**，适合演示三 Agent 的协作时序
- 墨刀强在**移动端模拟器 + 真机扫码预览**，适合做用户测试
- Xmind 强在**层级 + 关系**，适合架构沟通

## 1 · 设计哲学

**Three principles**：

1. **Restrained Confidence · 克制的自信**
   不靠饱和度堆砌视觉、不靠 Emoji 卖萌、不靠彩虹渐变制造科技感。设计的力量来自留白、字体节奏、对齐与层次。

2. **Editorial Warmth · 编辑式温度**
   产品是工具，但语气是杂志。中文衬线 + 西文 Serif 重音、合理的字号阶梯、对话式（而非命令式）的文案。

3. **Transparency · 透明**
   不藏 Agent 状态、不藏 LLM 推理过程、不藏数据存储位置。Memory 始终可观察。

## 3 · Typography · 字体

### 3.1 字族

| 用途 | 字族 | 备选 |
|---|---|---|
| 西文主字 | Inter | -apple-system / 系统 |
| 中文主字 | PingFang SC | Microsoft YaHei / 思源黑体 |
| 重音衬线 | Source Serif 4 | Songti SC（中文） |
| 数据/代码 | JetBrains Mono | SF Mono / Menlo |

### 3.2 字号阶梯

| Token | Size | Line | 用途 |
|---|---|---|---|
| `display` | 64-96 | 1.02 | Hero 标题 |
| `h1` | 40-64 | 1.1 | 页面主标 |
| `h2` | 28-44 | 1.1 | 区域标题 |
| `h3` | 22-28 | 1.2 | 卡片标题 |
| `lead` | 20 | 1.5 | 引导段落 |
| `body` | 16 | 1.55 | 正文 |

| `caption` | 12 | 1.5 | 标签 / 元信息 |
| `micro` | 10-11 | 1.4 | 法律 / Mono 标签 |

### 3.3 排版规则
- 字重：300 / 400 / 500 / 600 / 700 五档，不超过
- 字距：H1-H3 用 -0.02 ~ -0.035em；正文不调整
- 中文：避开 Light 200 字重，最小 400
- 标题：英文 Serif 重音字（如 _growth_）用 Italic 400

## 7 · Motion · 动效

### 7.1 时长

| 类型 | 时长 | 缓动 |
|---|---|---|
| 微交互 (hover) | 160ms | ease-out |
| 元素切换 | 180-240ms | cubic-bezier(0.2, 0.8, 0.2, 1) |
| 页面级 | 320-480ms | cubic-bezier(0.2, 0.8, 0.2, 1) |
| Skeleton shimmer | 1400ms | ease-in-out infinite |
| Agent 思考 | 1500ms | ease-in-out infinite |

### 7.2 动效原则
- ✅ 一切动效都有意义（指引 / 反馈 / 状态）
- ❌ 不使用纯装饰动效
- ✅ 尊重 `prefers-reduced-motion`
- ✅ 入场用「上浮 + 淡入」组合，避免左右移动

## 10 · Voice & Tone · 文案

### 10.1 语气原则
- **像懂你的朋友，不像 ChatBot**
- **诚恳，不奉承也不否定**
- **简短，单句不超过 30 字**

### 10.2 句式范例

❌ **不要**：
- "您好，欢迎使用 Yuki！我是您的智能助手..."
- "恭喜您完成了任务！您真棒！"
- "AI 正在为您智能拆解任务..."

✅ **要**：
- "早安，林同学"
- "今天还剩 2 项，先做硬的"
- "规划师拆解中"

### 10.3 Agent 个性

| Agent | 性格 | 范例语言 |
|---|---|---|
| 🎯 规划师 | 战略家 · 简洁 · 结构化 | "已为「考研复习」拆出 14 项任务" |
| ⚡ 执行官 | 教练 · 鼓励 · 具体 | "已完成 3/4，最后一项 30 分钟就能搞定" |
| 📊 复盘师 | 顾问 · 中性 · 洞察 | "本周高产时段是周一上午，硬任务可优先排在这里" |

## 13 · 可用性测试反哺

详见 [`USABILITY_TEST.md`](./USABILITY_TEST.md)。

设计规范不是一次性产物，**经过 2 轮可用性测试 + 3 版迭代**：

| 版本 | 关键改动 | 触发原因 |
|---|---|---|
| v0.8 (初版) | 三 Agent 颜色为饱和金 / 红 / 绿 | 用户反馈"太像彩虹 PPT，不专业" |
| v0.9 (二版) | 改用 OKLCH 同色相不同饱和度 | 解决了"花俏"问题，但仍有"分不清谁是谁" |
| **v1.0 (终版)** | OKLCH 金 / 蓝 / 青三色 + 每 Agent 独立图标 + 状态语言 | 用户测试 100% 区分三 Agent |

## 14 · 交互范式：轻量对话 + 结构化卡片

这是 Yuki 区别于纯 ChatBot 的关键设计决策。

**为什么不全用对话**：
- 对话堆积导致信息密度低
- 用户无法直接操作 AI 输出（如勾选任务）
- 无法可视化时间序列数据

**为什么不全用表单**：
- AI 价值不可见
- 用户难以表达模糊意图
- 缺乏自然交互的轻盈感

**双轨设计**：

```
┌──────────────────────────────────────┐
│  Header · 第 N 天 + 进度环              │
├──────────────────────────────────────┤
│  AgentStrip · 三 Agent 状态横幅         │ ← 卡片轨
├──────────────────────────────────────┤
│  Goal Card · 当前目标 + 任务树预览       │ ← 卡片轨
├──────────────────────────────────────┤
│  Today Tasks · 可勾选的结构化任务卡      │ ← 卡片轨
├──────────────────────────────────────┤
│  Activity Log · 三 Agent + 用户事件流    │ ← 卡片轨
├──────────────────────────────────────┤
│  ▼ Composer · 底部对话输入框           │ ← 对话轨
└──────────────────────────────────────┘
```

底部 Composer 接收自然语言 → 意图识别 → 路由到对应 Agent → AGent 输出渲染为**新的结构化卡片**或**更新现有卡片**，**永不堆积**对话气泡。
